# [DRAFT] L-CAP: Long-Term AI Collaboration Protocol 🛡️

**Deterministic Context Management & Semantic Continuity for LLM Projects.**

**L-CAP** — это открытый методологический протокол, разработанный для устранения **контекстной деградации** в сверхдлинных сессиях взаимодействия с ИИ. Он трансформирует хаотичный диалог в структурированный инженерный процесс, устойчивый к галлюцинациям и потере фокуса.

---

## 1. Проблема: Эффект «насыщения»
При достижении порога в 30–50 сообщений большие языковые модели (LLM) накапливают логический шум, теряют приоритеты первичных инструкций и начинают игнорировать ранние архитектурные решения. **L-CAP** решает это через дискретное квантование памяти и строгую иерархию данных.

## 2. Ключевые концепции
Протокол переводит работу из режима «чата» в режим управления жизненным циклом проекта (ALM):

*   **Immutable Genesis (Первичный импульс):** Самое первое сообщение пользователя в самом первом чате проекта. Оно никогда не подвергается дистилляции и переносится в каждую новую сессию в исходном виде («as is»). Это «генетический код» и точка сингулярности вашего проекта.
*   **Session Quanta (Кванты):** Автономные блоки опыта, нарезаемые по объективным триггерам времени (**Idle Threshold**) или объема (**Message Limit**). Каждый квант проходит процедуру дистилляции перед архивацией.
*   **Context Snapshot (Слепок):** Итоговый пакет данных, содержащий *Genesis* и иерархию дистиллированных *Квантов*.
*   **Notary Agent (Нотариус):** Системная роль ИИ в новой сессии, принимающей Snapshot как единственный верифицированный источник истины (Ground Truth).

## 3. Архитектура и Метрики (Field Log)
Каждое решение в L-CAP размечается объективными индексами для обеспечения прозрачности:
- **Global Index:** Сквозная нумерация реплик через все сессии проекта.
- **Session Delta (D):** Количество сообщений в кванте. Отражает «физический вес» и проработанность этапа.
- **Time Gap:** Длительность паузы перед квантом. Индекс человеческой рефлексии и «выдержки» идеи вне взаимодействия с моделью.
- **Density Factor:** Плотность диалога (msg/min). Высокая плотность активирует режим **High Resolution** (сохранение полных логических цепочек — «мяса» проекта).
- **Rejected Paths:** Реестр тупиковых путей и ошибок для предотвращения их циклического повторения моделью.

## 4. Конфигурация протокола (Default Config)
Для инициализации L-CAP в начале проекта рекомендуется задать следующие параметры в системном промпте:
```yaml
Idle_Threshold: 15m   # Порог неактивности для закрытия кванта
Message_Limit: 30     # Лимит сообщений для принудительного сброса энтропии
Density_Trigger: 0.5  # Порог плотности для детальной архивации (msg/min)
```

## 5. Пример Snapshot для миграции
При переносе контекста в новую сессию используется структура вида:

[IMMUTABLE GENESIS]: Постановка задачи на разработку GBDT Runtime для FPGA.

```
[SESSION 01-30 | D: 30 | Gap: 0] CORE: Архитектура конвейера утверждена.
[SESSION 31-45 | D: 15 | Gap: 18h | HD] LOGIC: Оптимизация таймингов после рефлексии.
[REJECTED]: Использование динамической памяти (не проходит по задержкам).
[CUSTOM]: [Status: Verified], [Logic_Depth: 12]
```

## 🌍 True Story: Как это появилось
L-CAP родился не в офисе, а во время планирования большой одиночной мото-экспедиции.

Проект был сложным: погодные окна, графики ТО, логистика запчастей и границы. На 40-м сообщении мой ИИ-ассистент начал «сдавать»: путал интервалы обслуживания и забывал про утвержденные точки маршрута. 

Мне нужно было решение, чтобы не потерять наработки месячного планирования. Так появился этот метод «сброса и дистилляции». Если протокол помог справиться с логистикой через полконтинента, он справится почти с любой сложной инженерной или творческой задачей.
